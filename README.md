# A/B Test Quality Control

Инструмент для **стандартизированного анализа и контроля качества A/B-тестов**.

Проект предназначен для того, чтобы перед статистическим анализом проверить корректность входных данных и самого экспериментального дизайна, затем выполнить стандартизированный набор статистических расчётов и сохранить воспроизводимый результат каждого запуска.

Основная идея проекта:

```text
RAW DATA
   ↓
DATA QUALITY
   ↓
STATISTICAL ANALYSIS
   ↓
INTERPRETATION
   ↓
REPRODUCIBLE RESULTS
```

Проект построен как универсальный шаблон: при замене входного датасета последовательность проверок и анализа остаётся одинаковой.

---

## About the project

A/B-тест позволяет сравнить две группы пользователей и определить, отличается ли целевая метрика между вариантами.

Однако статистический расчёт имеет смысл только тогда, когда исходные данные и экспериментальный дизайн корректны.

Поэтому проект решает две задачи:

1. **Контроль качества эксперимента**
2. **Стандартизация статистического анализа**

Перед расчётом результата система проверяет:

* структуру данных;
* наличие обязательных колонок;
* пропуски;
* уникальность пользователей;
* корректность групп;
* корректность значений целевой метрики;
* наличие обеих групп;
* соответствие фактического распределения пользователей ожидаемому через **Sample Ratio Mismatch (SRM)**.

После успешного прохождения Data Quality выполняется статистический анализ A/B-теста.

---

## Why A/B test needs data quality control

Ошибка в данных может привести к статистически корректному расчёту, но некорректному выводу.

Например:

```text
Дубликаты пользователей
        ↓
Один пользователь учитывается несколько раз
        ↓
Размер выборки и конверсия искажены
        ↓
Статистический результат становится ненадёжным
```

Или:

```text
Ожидалось распределение 50/50
        ↓
Фактически 80/20
        ↓
Возможна проблема с рандомизацией
        ↓
A/B-тест требует дополнительной проверки
```

Поэтому статистический анализ запускается **только после прохождения Data Quality**.

# What the pipeline checks

## 1. Schema validation

Проверяется наличие всех обязательных колонок:

```text
user_id
group
converted_observed
```

Если необходимая колонка отсутствует, анализ останавливается.

---

## 2. Missing values

Проверяется наличие пропущенных значений в ключевых полях.

Для текущего эксперимента:

```text
user_id
group
converted_observed
```

Пропуски в этих полях могут сделать дальнейший анализ некорректным.

---

## 3. User uniqueness

Каждый пользователь должен присутствовать в эксперименте только один раз.

Проверяется уникальность:

```text
user_id
```

Это позволяет избежать ситуации, когда один пользователь искусственно увеличивает размер выборки.

---

## 4. Valid groups

Проверяется, что в эксперименте используются только предусмотренные группы:

```text
A
B
```

Неизвестные значения групп приводят к ошибке Data Quality.

---

## 5. Valid metric values

Для текущей бинарной метрики `converted_observed` допустимы только:

```text
0 — не сконвертировался
1 — сконвертировался
```

Другие значения считаются некорректными.

---

## 6. Group availability

Проверяется наличие пользователей в обеих группах.

Эксперимент не может быть корректно проанализирован, если:

```text
A = 0 пользователей
```

или

```text
B = 0 пользователей
```

---

## 7. Sample Ratio Mismatch

**Sample Ratio Mismatch (SRM)** — проверка соответствия фактического распределения пользователей между группами ожидаемому.

Например, для теста 50/50:

```text
Expected:

A = 50%
B = 50%
```

Фактическое распределение сравнивается с ожидаемым с помощью χ²-теста.

Проверка позволяет обнаружить потенциальные проблемы с распределением пользователей между вариантами эксперимента.

Для текущей конфигурации:

```python
EXPECTED_GROUP_RATIO = {
    "A": 0.5,
    "B": 0.5
}
```

Порог статистической проверки:

```python
SRM_ALPHA = 0.05
```

SRM рассматривается именно как **контроль качества эксперимента**, а не как часть расчёта конверсии.

# Statistical analysis

После прохождения всех Data Quality checks запускается статистический анализ.

## Conversion

Для каждой группы рассчитывается конверсия:

```text
conversion = conversions / users
```

Например:

```text
A: 166 / 214 = 77.57%

B: 153 / 212 = 72.17%
```

---

## Absolute uplift

Показывает абсолютную разницу конверсий:

```text
Absolute uplift = Conversion B - Conversion A
```

Например:

```text
72.17% - 77.57% = -5.40 percentage points
```

---

## Relative uplift

Показывает относительное изменение относительно группы A:

```text
Relative uplift =
(B - A) / A
```

Например:

```text
-6.96%
```

Absolute и relative uplift описывают **наблюдаемый эффект**, но сами по себе не показывают его статистическую значимость.

---

## Z-test

Для сравнения двух пропорций используется z-test.

Он позволяет проверить гипотезу о равенстве конверсий двух групп.

В рамках теста:

```text
H₀: conversion A = conversion B

H₁: conversion A ≠ conversion B
```

---

## P-value

P-value используется для оценки результата статистического теста относительно выбранного уровня значимости:

```text
α = 0.05
```

Если:

```text
p-value < α
```

результат считается статистически значимым на выбранном уровне значимости.

Если:

```text
p-value ≥ α
```

недостаточно статистических оснований утверждать, что между группами существует различие.

Важно: отсутствие статистически значимого различия не означает, что группы гарантированно одинаковы.

---

## Confidence interval

Для разницы конверсий рассчитывается 95% доверительный интервал:

```text
CI = [lower, upper]
```

Интервал показывает диапазон значений разницы, согласующийся с данными при выбранном уровне доверия.

В текущем проекте интервал рассчитывается для:

```text
Conversion B - Conversion A
```

Если интервал включает `0`, это согласуется с отсутствием статистически значимого различия.

# Why these checks are separated

В проекте намеренно разделены этапы **Data Quality**, **Statistical Analysis** и **Interpretation**.

```text
DATA QUALITY
      ↓
STATISTICAL ANALYSIS
      ↓
INTERPRETATION
      ↓
RESULTS
```

Каждый этап отвечает за свою задачу.

### Data Quality

Отвечает на вопрос:

> Можно ли использовать эти данные для анализа?

### Statistical Analysis

Отвечает на вопрос:

> Что показывают данные с точки зрения статистики?

### Interpretation

Отвечает на вопрос:

> Как корректно объяснить полученный статистический результат?

Такое разделение позволяет не смешивать проблемы качества данных со статистическими выводами.

# Example

Пример результата одного из запусков:

```text
Group A:
166 / 214
Conversion: 77.57%

Group B:
153 / 212
Conversion: 72.17%

Absolute uplift:
-5.40%

Relative uplift:
-6.96%

Z-statistic:
-1.285

P-value:
0.1988

95% CI:
[-13.62%; 2.82%]

Alpha:
0.05
```

При этом:

```text
p-value = 0.1988 > 0.05
```

Поэтому статистически значимого различия между группами на уровне `α = 0.05` не обнаружено.

Наблюдаемая разница в конверсиях сохраняется как описание данных, но не интерпретируется автоматически как доказанный эффект варианта.

```bash
python -m venv .venv
source .venv/bin/activate
```

Установить зависимости:

```bash
pip install pandas scipy
```

Запустить A/B-тест:


# Reproducibility

Каждый запуск получает уникальный `run_id` на основе времени запуска:

```text
YYYY-MM-DD_HHMMSS
```

Например:

```text
2026-09-16_223455
```

Результаты разных запусков не перезаписывают друг друга.

Это позволяет:

* сохранять историю экспериментов;
* сравнивать результаты разных запусков;
* анализировать изменения входных данных;
* восстанавливать результаты конкретного запуска;
* использовать результаты как артефакты аналитического pipeline.

# Project philosophy

Основной принцип проекта:

> **Сначала проверяем данные и эксперимент, затем считаем статистику, и только после этого интерпретируем результат.**

Таким образом, A/B-тест рассматривается не как один статистический расчёт, а как последовательный воспроизводимый процесс:

```text
RAW DATA
   ↓
DATA QUALITY
   ↓
EXPERIMENT VALIDATION
   ↓
STATISTICAL ANALYSIS
   ↓
INTERPRETATION
   ↓
REPRODUCIBLE RESULTS
```

Цель проекта — **стандартизировать процесс A/B-анализа и сделать контроль качества эксперимента воспроизводимым**.
